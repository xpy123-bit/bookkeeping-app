# bookkeeping-app — 交接文档

移动优先、本地优先的记账 PWA。核心能力：导入**微信支付**与**支付宝**导出的账单，
自动分类、去重、核对，并给出月度报表与预算超支提醒。

**本文件面向接手开发的 agent。** 读完后应当能直接开工：所有命令、不变量、
已核实的格式事实、以及未完成项都在下面。

## 2. 必须遵守的不变量

改动这个项目时，下面每条都是硬约束。违反它们会产生**静默的错数据**，比报错危险得多。

1. **金额一律用整数「分」**（`amountCents`）。绝不用浮点数。`0.1 + 0.2 !== 0.3`
   会直接导致对账失败。见 `src/domain/money.ts`。
2. **解析一律按字段名，不按行号/列号**。平台会调整噪声行数与列序。
   硬编码偏移量会在某次平台更新后静默解析错数据。见 `src/import/csv.ts` 的
   `buildColumnIndex` / `readColumn`。
3. **行字段数少于表头列数时必须拒绝该行**（`reason: 'fewer-fields'`）。
   中间少一列会让后面整体错位，而「收/支」和「金额」可能恰好落在正确位置，
   于是错数据被无声记账。**字段数多于表头是合法的**（支付宝备注为空时行尾多一个逗号）。
4. **中性交易单独建模为 `direction: 'transfer'`，绝不当支出**。
   充值/提现/理财/信用卡还款是账户间搬钱，当成支出会让资产恒等式崩掉。
   统计时 `signedCents('transfer', n) === 0`。
5. **时间用本地墙上时间字符串 `'YYYY-MM-DD HH:mm:ss'`**，不转 UTC。
   账单里的时间就是持卡人本地时间，转来转去只会引入跨日误差。
6. **编码检测用确定性判据**：严格 UTF-8 解码是否抛错。不要用 `chardet`/`jschardet`
   —— GBK/GB2312/GB18030 统计特征高度相似，误判率高。
7. **去重键优先用平台订单号**（`buildDedupeKey`），并在 IndexedDB 层对
   `dedupeKey` 建唯一索引。用户会反复导入同一个月账单，这是真实习惯。
8. **Service Worker 绝不能缓存 `/auth/*`**（`vite.config.ts` 的
   `navigateFallbackDenylist`）。被缓存的 OAuth 回调可能重放 code/state 组合。

## 3. 已核实的账单格式事实

以下全部经过**真实账单文件逐字节核对**，不是从二手教程抄的，也不是推测。
改动解析器前请先读这一节。

### 3.1 导出形态

- 微信和支付宝导出的**都是加密 ZIP**，内层才是 CSV。UI 必须支持「拖入 ZIP + 填密码」。
- **微信解压密码**：通过「微信支付」公众号的「账单文件发送成功通知」下发，**每人不同**，
  常见形态是 6 位数字。**不是**从用户填写的邮箱/手机号推导出来的（该说法无一手来源）。
- **支付宝解压密码**：**实名认证身份证号后 6 位**，末位 X 需大写。
- **微信近期导出可能是 `.xlsx`**（本应用会明确提示并拒绝，需另存为 CSV）。
- ZIP 是传统 ZipCrypto，不是 AES。`@zip.js/zip.js` 可解。

### 3.2 编码（最容易翻车的地方）

| 来源 | 编码 | 验证方式 |
| --- | --- | --- |
| 微信支付账单 | **UTF-8** | `tests/fixtures/wechat-real.csv` 严格 UTF-8 解码成功 |
| 支付宝账单 | **GBK / GB18030** | 同一文件严格 UTF-8 解码**失败** |

Node 与浏览器均原生支持 `new TextDecoder('gb18030')`，**不需要 iconv-lite**。

### 3.3 微信列定义（11 列，顺序固定）

```
交易时间,交易类型,交易对方,商品,收/支,金额(元),支付方式,当前状态,交易单号,商户单号,备注
```

- 噪声行：前 16 行是元信息/统计/说明，**第 17 行是表头，第 18 行起是数据**。
  **但代码里绝不能硬编码 17** —— 已按字段名定位。
- 分隔线：`----------------------微信支付账单明细列表--------------------`
- `收/支` 取值：`收入` / `支出` / **`/`（字面斜杠 = 中性交易）**。
  `/` 不是空值，只判空会把提现/充值误判为支出。
- 金额形态：`¥28.16`（带货币符号）。
- **`交易单号`/`商户单号` 尾部带一个 `\t`**（平台为阻止 Excel 转科学计数法）。
  分词器已 trim，不 trim 会让去重键带上不可见字符。
- **提现要扣服务费**：备注形如 `服务费¥0.10`，需从本金中减去。
- `当前状态` 是**开放字符串集合，不要建枚举**。观测值包括 `支付成功`、`已存入零钱`、
  `已转账`、`朋友已收钱`、`已收钱`、`提现已到账`、`充值完成`、`已到账`、`充值成功`。
- 中性交易类型用**包含**匹配（真实值带后缀，如 `转入零钱通-来自工商银行(9876)`）：
  `零钱充值`、`零钱提现`、`信用卡还款`、`转入零钱通`、`零钱通转出`、`购买理财通`。
- 顶部统计块：`共43笔记录` / `收入：1笔 0.35元` / `支出：1笔 28.16元` / `中性交易：0笔 0.00元`

### 3.4 支付宝列定义（三种变体）

**变体 A — 新版（2022 至今，App「开具交易流水证明」），12 列：**

```
交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注
```

**变体 B — 2020–2021：字段名相同，但列序不同**（`收/支` 在第 0 列，`交易时间` 在末列）。
因为实现是**按名取值**，A 与 B 天然兼容，无需分别处理。

**变体 C — 旧版 PC 网页导出，16 列**：字段名完全不同
（`交易号`/`商品名称`/`金额（元）`/`交易创建时间`/`交易来源地`/`资金状态`），
且不含付款账户。**已明确拒绝**并提示改用 App 导出。

- 表头字段名**带大量填充空格**（`交易时间            ,交易分类`）→ **必须 trim 后按名匹配**。
- 噪声行数随版本变化（实测表头在第 24 行；参考实现分别用 22 和 26）→ **不要硬编码**。
- `收/支` 取值：`支出` / `收入` / `不计收支` / **空字符串** / `其他`（`其他` 仅见于变体 B）。
  **空字符串与 `其他` 都按中性处理，绝不能当支出。**
- 退款行商品说明带 `退款-` 前缀，`交易状态 = 退款成功`。
- 顶部统计块用「**不计收支**」而非微信的「中性交易」：
  `共66笔记录` / `收入：1笔 28.50元` / `支出：63笔 16.54元` / `不计收支：2笔 16.37元`

### 3.5 退款与关闭的配对规则

两家都把退款作为**独立一行**，而原始支出行仍然保留。不配对的话同一笔消费会计两次。

- 配对依据：订单号相同（或以订单号前缀相同 + 金额相等兜底）。
- 微信：`direction === 'income' && status.includes('退款')` 的行找原支出。
- 支付宝：`status === '退款成功'` 的行找原支出。
- 配对的**两行同时剔除**，并记入 `skipped`。
- 支付宝 `交易状态 === '交易关闭'` 的行直接剔除（未产生资金流动）。
- 未配对成功的退款**保留为收入并产生 warning**，不静默丢弃。

### 3.6 导入后自检

账单顶部自带统计块 → 与解析结果比对 → 不一致就提示用户。
这是发现「平台格式变体」最便宜的护栏，见 `buildSelfCheckNotes`。

> 注意：`tests/fixtures/wechat-real.csv` 的声明值是 43 笔而实际只有 27 条数据行
> —— 该夹具被上游裁剪过，因此**声明值与实际值不一致是预期的**，不要把它当 bug 去改。

## 6. 登录接入：硬约束（已核实）

**先读完这节再动手，否则容易在走不通的方向上花掉几周。**

| 渠道 | 个人主体（无公司、无营业执照） |
| --- | --- |
| **支付宝** | ✅ **可申请、可上线**（官方支持账号类型含「个人账号（含个体工商户）」） |
| **微信** | ❌ **走不通**。网站应用登录要求公章 + ICP 备案域名 + 备案主体与认证主体一致，个人无法通过应用审核 |

**支付宝的三个关键事实：**

1. **限制在「资料」而非「创建」**：个人可创建应用并拿到稳定的 `user_id` / `open_id`，
   但「获取会员信息」权限的隐私申请**要求企业认证**，所以**拿不到昵称和头像**，
   需自己让用户填。→ 按 **identity-only provider** 设计，`NormalizedIdentity`
   的 name/avatar 必须是可选的。
2. **沙箱无需商业资质**即可完整联调，官方明确「在沙箱环境中调用接口无需具备所需的商业资质」。
3. **端点地址（网上大量教程是错的）**：

```
生产授权  https://openauth.alipay.com/oauth2/publicAppAuthorize.htm
生产网关  https://openapi.alipay.com/gateway.do
沙箱授权  https://openauth-sandbox.dl.alipaydev.com/oauth2/publicAppAuthorize.htm
沙箱网关  https://openapi-sandbox.dl.alipaydev.com/gateway.do
```

> ⚠️ 广泛流传的 `openauth.alipaydev.com` / `openapi.alipaydev.com` **已失效**（网关返回 502）。
> 连支付宝官方文档里的一段 Java 示例都仍在用旧地址。必须用带 `-sandbox.dl` 段的地址。

**其他必须知道的事实：**

- 支付宝 **H5 授权页只能在支付宝客户端内打开**，手机浏览器（Safari/Chrome）会报错。
  纯 Web 场景下桌面端扫码更可靠。
- 支付宝**正在把用户标识从 `user_id` 迁移到 `open_id`**（「未来推出的新产品将只支持 openid」）。
  → DB 里要**同时存标识符和它遵循的标准**（如 `subject_standard`），不要只存 `user_id`。
- 支付宝对 `state` 有限制：**base64 后 ≤100 字符，且不能含中文**。
- **微信支付宝都不是标准 OIDC 提供方**，`openid-client` / `oauth4webapi` 接不上。
  微信生态的 Node 库基本已停维护（`wechat-oauth` 最后发布 2018 年）→ 几个 HTTP 调用自己写。
  支付宝用官方 `alipay-sdk`（做 RSA2 签名，手写易错）。
- 微信还有坑：2022 年起异常使用 `snsapi_userinfo` 会进入快照页模式，返回
  **`is_snapshotuser: 1` 的虚拟账号**，后端**必须拒绝**，否则会给临时虚拟用户建号。
- 微信身份应存 **`unionid`**（不是 `openid`，后者是「用户+单个 AppID」维度）。

**安全清单（接入时逐条核对）：**

- `client_secret` 只在服务端；微信官方明确要求 `access_token` **只保存在服务器**
- `state` 用**服务端保存的一次性记录**（不要 sessionStorage —— PWA 在 iOS 上被回收会丢）
- `redirect_uri` 必须是**服务端常量**，绝不从 `Host`/`X-Forwarded-Host` 推导（开放重定向）
- Cookie 用 `SameSite=Lax`（`Strict` 会破坏 OAuth 回跳）
- Service Worker 不缓存 `/auth/*`（已配）
- 推荐**不持久化**提供方令牌：换取 → 归一化 → 丢弃
- 用户表唯一约束用 `UNIQUE (provider, subject)`
- 开发态 mock 登录**必须走真实 provider 路径**，不能是绕过；生产环境从注册表移除而非返回 403

当前 `server/index.ts` 已有渠道注册表与状态接口：

```bash
curl http://127.0.0.1:8787/api/health
```
